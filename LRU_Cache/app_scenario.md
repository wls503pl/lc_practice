实现一个固定容量的缓存（LRU Cache = Least Recently Used Cache）

你需要设计一个数据结构，支持两个操作，且都要求 O(1) 时间复杂度：

get(key)：根据 key 查找对应的 value。
如果找到了，返回这个 value，同时把这个 key 标记为"最近被访问过"。
如果没找到，返回一个表示"不存在"的结果（比如 -1 或 nullptr）。
put(key, value)：插入或更新一个 key-value 对。
如果 key 已经存在，更新它的 value，并标记为"最近访问过"。
如果 key 不存在，插入一条新的记录。
如果插入后缓存里的元素个数超过了容量上限，需要淘汰掉"最久没有被访问过"的那个元素。
用一句话概括这个数据结构的"记忆规则"

想象你桌上只能放 3 本书（容量=3）。

每次你翻看某本书（get）或者拿到一本新书放上桌（put），就把它放到最上面。
桌子放满了，你又拿了本新书要放，就把最下面那本（也就是最久没碰过的那本）从桌上拿走扔掉。

这就是"LRU"（Least Recently Used，最近最少使用）淘汰策略。

为什么这道题"有意思"（面试考点）

难点不在于逻辑本身（逻辑很直观），而在于：怎么同时做到

通过 key 快速查找（这个容易想到用哈希表 unordered_map）
但哈希表本身不记录"谁最近被用过"这种顺序信息
而且每次访问后，还要把这个元素挪到"最近使用"的位置，还不能是 O(n) 的搬移

所以真正的考点是：如何设计一个数据结构，既能 O(1) 查找，又能 O(1) 地调整访问顺序、O(1) 地删除最旧元素。
------------------------------------------------------------------------------------------------------
第一步：为什么单独一个数据结构都不够

只用哈希表 unordered_map<key, value>：

查找 O(1)，没问题。
但是哈希表内部元素是无序的，没法知道"谁是最久没被访问的那个"。所以淘汰的时候你没法快速找到该删谁。

只用链表 list（把访问过的元素移到队头，队尾就是最久未用的）：

顺序问题解决了：队头 = 最近用的，队尾 = 最久没用的，删除队尾就是淘汰目标，O(1)。
但是 get(key) 要找到 key 对应的节点，只能从头到尾遍历链表，O(n)，不满足要求。

第二步：怎么结合

关键的一个技巧：哈希表里存的不是 value，而是"链表节点的位置（迭代器/指针）"。

unordered_map<key, 链表节点地址> + 双向链表（节点里存 key 和 value）

为什么要双向链表，不要单向？因为：

你要把一个节点从链表中间"摘出来"，然后"插到队头"。
单向链表要删除一个节点，需要知道它的前驱节点（不然接不上），只能从头遍历找前驱，O(n)。
双向链表每个节点自己就存着 prev 和 next，所以"摘出任意一个节点"是 O(1) 的，不需要遍历。

第三步：两个操作具体怎么做

get(key)：

去哈希表里查 key，找到对应的链表节点（O(1)）。
如果没找到，返回"不存在"。
如果找到了：
把这个节点从当前位置摘下来，塞到链表最前面（代表"刚刚被访问过"）。因为是双向链表，这个"摘下来再塞到前面"的操作是 O(1)（C++ 里这一步用 list::splice 一行搞定，不需要真的删除再新建节点）。
返回节点里存的 value。

put(key, value)：

先查哈希表看 key 存不存在。
如果存在：直接更新节点里的 value，然后跟 get 一样，把这个节点挪到链表最前面。
如果不存在：
在链表最前面新建一个节点，存 (key, value)。
在哈希表里记录 key -> 这个新节点。
检查一下：现在元素总数是不是超过了容量上限？
如果超了，说明该淘汰了：链表最后面的节点就是"最久未使用"的，把它从链表尾部删掉，同时从哈希表里把它的 key 也删掉（这一步很重要，容易漏掉——哈希表和链表必须同步维护，不然哈希表里会留着一个指向"野指针"的记录）。

在交易系统里，LRU 缓存是个非常常见的组件，核心思路都是"内存/查找资源有限，只保留最近最可能被用到的数据"。结合你在撮合引擎方面的背景，列几个具体场景：

1. 订单查找缓存（Order Lookup Cache）

撮合引擎里订单簿（order book）本身通常用红黑树/跳表维护价格优先级，但撤单（cancel）操作需要用 order_id 快速定位到订单在哪个价位、哪个位置。

如果订单总量很大，不可能把所有历史订单都常驻内存。
用 LRU：最近下的、最近被查询过的订单留在缓存里，O(1) 查到指针直接操作；老订单（已成交或很久没动静的）被淘汰，释放内存。
2. 行情快照/Tick 数据缓存
追问里提到的"低延迟行情缓存"就是这个场景：多个下游模块（风控、策略、UI）都要读某些 symbol 的最新价格/深度快照。
只给"最近活跃的 symbol"保留在快速缓存里，冷门 symbol 的数据可以懒加载或者从慢速存储读。
这也是为什么会有"array + intrusive linked list"的追问——避免 std::list 节点在堆上到处分配导致 cache miss，这在行情这种要求微秒级延迟的场景很关键。
3. 账户/持仓信息缓存
撮合/风控系统每次成交都要读取用户的余额、持仓、风控参数。
全量用户数据放内存代价太高，用 LRU 缓存活跃交易用户的账户信息，不活跃用户的数据落盘或走数据库，需要时再加载回来。
4. 交易对/合约元数据缓存
每个 symbol 有一堆静态配置：最小下单量、价格精度、手续费率、合约乘数等。
这类数据变化不频繁但查询极其频繁（几乎每笔订单都要查），用 LRU 或者干脆全量常驻（如果 symbol 数量不多的话，可能都不需要淘汰，直接哈希表就够了——这也是面试官可能会追问的点："这个场景真的需要 LRU 吗？"）。
5. 撮合引擎的"最近成交"缓存（Trade Cache）
提供给客户端 API 查询"最近成交记录"（recent trades）时，不需要每次都去查数据库，用 LRU 或者固定大小的环形缓冲区（ring buffer）保留最近 N 笔成交。
